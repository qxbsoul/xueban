# v1.5.21 判题系统可靠性专项 — 验收报告

日期：2026-11-27
目标：定位并修复大规模判题失败率高、队列停滞、失败状态不持久、前端失败列表不自动更新的根因；不以“加重试次数/加超时/改前端”掩盖问题。

---

## 1. 修改文件

**后端**
- `xueban-backend/xueban/api/xueban_teacher.py`
  - HTTP 客户端、12 类错误分类、重试管理器、并发 Worker、原子领取、心跳/恢复、每题状态、幂等、契约修复、重判进度。
- `xueban-backend/xueban/services/xueban_store.py`
  - `db.update()` 原子条件更新；每线程独立 SQLite 连接/事务深度，修复并发 commit 串线。
- `xueban-backend/xueban/services/learning_analysis.py`
  - `ensure_model()` 加线程锁，修复并发建表/加列 duplicate column。
- `xueban-backend/xueban/server.py`
  - 启动时自动恢复可恢复判题任务。
- `xueban-backend/backend-openapi.json`（重新生成）
- 测试：`tests/test_v1521.py`、`_v1521_http_worker.py`、`_v1521_queue_worker.py`、`_v1521_real_sample.py`；受影响旧测试按“超分改为复核”语义更新。

**前端**
- `xueban-web/src/components/BatchGrading.tsx`
  - FailurePanel 依赖 `expected` 并在任务活动时 2.5s 轮询；重判进度显示成功/待复核/失败。

## 2. 故障分析表

| 故障 | 文件/函数 | 根本原因 | 修改方案 | 验证 |
|---|---|---|---|---|
| SSL EOF / IncompleteRead / RemoteDisconnected 高发 | `xueban_teacher.llm_grade` | 单次 `urllib.urlopen(timeout=45)`；连接、读取、整体超时混为一个；没有连接健康检查/重建；部分响应无法区分 | 改为 `http.client`：连接超时/读取超时/整体 deadline 分离；完整 `read()`；异常立即丢弃连接，下一次重建；线程本地连接复用；HTTP 状态/JSON 信封校验 | 本地 Mock HTTP：IncompleteRead、slow、SSL、429、500 均恢复；`test_v1521` |
| 失败重试不区分错误 | `call_grader_with_retry` | 只按 `retryable` 布尔；429 没有 Retry-After；5xx/网络/解析混用 | 统一 `NETWORK_ERROR / READ_TIMEOUT / CONNECT_TIMEOUT / INCOMPLETE_RESPONSE / SSL_ERROR / RATE_LIMIT / SERVER_ERROR / RESPONSE_PARSE_ERROR / RESPONSE_VALIDATION_ERROR / DATA_VALIDATION_ERROR / SCORING_RULE_MISMATCH / UNKNOWN_ERROR`；仅可恢复类重试；429 遵守 Retry-After；指数退避+抖动 | 429/500/超时/SSL 恢复；非法 JSON/数据错误不盲重试 |
| 单 Worker 串行，队列停滞 | `_run_job_once` | 只有一个循环；没有并发控制；一条请求占用整个队列 | 新增 `_worker_loop`：可配置并发 1–8；固定线程数；原子条件领取；单题失败不退出其他 Worker；最多三轮低并发补偿 | 并发 2/3/5/8 压测全部 12/12 成功、无重复领取 |
| 同一题重复领取 | `_claim_item` | 先 SELECT 再 UPDATE，竞争失败直接 return，其他 Worker 提前退出 | 单条 `UPDATE ... WHERE id=? AND status='pending'` 条件领取；竞争失败重试下一道（8 次） | 压力测试 `duplicate_calls=0` |
| 超时/异常导致 Worker 永久占用 | 旧 `_run_job_once` | 没有请求级超时上限/连接释放；异常在循环外会终止线程但 job 仍 running | 连接/读取/整体超时；每 Worker 独立连接；单题异常落库后继续；心跳线程每 10s 更新；running 心跳 90s 失联自动归 paused+重排 | restart 场景 recovered=1、最终 completed |
| 800 条任务卡在 712 | `run_job` / `ensure_job_worker` | 后台任务丢失/锁冲突丢任务；queued 无补启动；running 失联只等 300s | 锁冲突延迟重试；queued/retrying/失联 paused 自动补 Worker；启动时 `recover_jobs_on_startup()`；心跳线程 | 重启恢复、断点续接测试 |
| 失败状态只在内存/字段缺失 | `record_attempt` / `_process_item` | item 只有 `last_error`；attempt_count 按领取次数而非真实请求；错误类型/详情/结果 ID 未持久化 | v9 增加 `max_attempts/last_attempt_at/last_error_type/last_error_detail/result_id`；每次 attempt 更新；成功/失败均落 completed_at；attempt_count 以 attempts 表为准 | `test_v1521` 校验 attempt_count/result_id/错误类型 |
| 超时后重复判题/重复结果 | `grade_answer` | 幂等只检查 item.completed；结果已入库但 item 未标完成的窗口会重判 | 检查本次领取后已有非 failed 版本，直接复用并补 item；成功题目重试不覆盖 | `one_valid_result`: runs=1、calls=2（网络失败+成功） |
| 评分点超分/步骤分不闭合导致整题永久失败 | `validate_llm_result` / `_validate_point_link` | 单点 awarded > max、步骤分 != 总分、点为合计 > 总分全部 raise | 单点超分截断到原始满分并标记 review；总分按步骤/评分点合计修正；步骤分不闭合进入复核；不再整题失败；不伪造成功 | 真实失败从 37 降到 1；`test_v1521`/taxonomy |

| SQLite 并发 commit 串线 | `xueban_store` | 单连接 + 全局 `_TX_DEPTH`，多线程 commit 互相影响 | 每线程独立连接；事务深度线程本地；`db.update()` 原子行数 | 并发压测 806 条无 commit 错误 |
| 失败列表不自动刷新 | `FailurePanel` | effect 依赖只有 `[jobId,page]`，`expected` 变化不重新请求 | 依赖 `expected`；活动任务 2.5s 轮询；卸载/请求 abort；失败数变化自动刷新 | 前端 build + 代码路径；后端失败数即时落库 |
| 用户看到 Python 堆栈 | `job_failures` | 只返回原始 error_type/last_error | 用户可读 `KIND_LABELS` + `readable_reason`；技术详情保留 `error_detail/attempts/exception_class` 可展开 | UI 字典与详情 |

## 5. 真实数据验证（当前赛题）

**起点（v1.5.21 开始时 job_23a2d13b29）**
`806 = 738 成功 + 15 待复核 + 53 失败`。

**第一轮：重判 53 条失败（旧校验）**
- 16 完成 / 37 失败，失败率 69.8%
- 平均 attempts 4.06，P95 25s，attempts 283
- 失败：contract 33、scoring mismatch 3、answer_missing 1
- 说明：这 53 条是此前用户重跑后剩下的更难样本，不是 v1.5.20 的 60 条原样本。

**第二轮：对剩余 37 条启用“超分截断到满分+复核、步骤/评分点闭合修正”**
- 37 条：5 有效成功 + 31 待复核 + 1 失败（answer_missing）
- 失败率 2.7%；重判进度 5/31/1
- 最终任务：`806 = 759 成功 + 46 待复核 + 1 失败`，计数一致
- 总失败率 0.12%；严格有效成功率 94.2%，复核率 5.7%

**与 v1.5.20 对比**

| 指标 | v1.5.20 | v1.5.21 |
|---|---|---|
| 成功 | 658 | 759 |
| 待复核 | 12 | 46 |
| 失败 | 136 | 1 |

说明：新增 34 条复核不是“成功”；它们原先会因评分点超分/步骤不闭合整题失败，现在保留模型原始分并截断到合法满分，交人工复核。没有把失败伪装成成功。

## 6. 未解决 / 限制

1. **唯一最终失败是 answer_missing**：原始作答与过程都为空，属于数据缺失，不能判题；保留失败原因。
2. **46 条待复核**：模型仍出现评分点重复给分/步骤分不闭合；已截断到合法满分，但没有可靠证据判定为完全正确，不能直接算成功。
3. **真实样本不是严格 60 条**：开始时只剩 53 条失败，未凑数；第一轮 53，第二轮 37。没有为了凑 60 伪造记录。
4. **并发压测是 Mock 模型**：并发 2/3/5/8 验证了队列/领取/持久化，不是 8 路真实 API 压测；真实重判使用并发 2。
5. **P95 25s** 受模型单次响应影响；读取超时默认 90s、整体 120s，没有继续放大。
6. **历史 attempts 中仍有旧 `model_error` 记录**：这是旧版本留下的技术诊断，新记录按 12 类写入；不删除历史。
