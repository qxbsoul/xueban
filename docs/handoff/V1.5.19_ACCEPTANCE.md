## 1. 根因（对应任务书要求解释的六个问题）

### 1.1 为什么实际判题时仍显示“排队中”
- `_run_job_once` 只在状态为 `queued/paused` 时把任务置为 `running`；`run_job` 用非阻塞锁，如果上一个 worker 还持有锁，本次调用**直接 return**，任务永远停在 `queued`。
- `jobs()/job()` 只回收心跳过期的 running，**没有 queued 的补启动逻辑**；进程重启后后台任务丢失，queued 任务无人认领。
- 前端轮询在状态离开 `running/queued/pausing` 后把 interval 标记为 stopped，且 effect 只依赖 `job.id`，后续状态变化不会重新启动轮询。
- 旧 `job()` 返回的 `job.completed` 同时包含成功与待复核，`job.failed` 与 item 实际失败数也不一致，造成“数字像没动”。

### 1.2 为什么失败重判后进度条不自动更新
- `retry_job` 把 failed item 直接改成 `pending`，`job.failed` 瞬间减少、`processed` 回退，进度百分比反而下降。
- 没有任何“重判进度”字段，前端只能看整体进度。
- 重判后没有独立轮询；页面上的数字只在下一次手动操作（pause/resume）触发 `setJob` 时才刷新。

### 1.3 为什么暂停以后才触发进度更新
- 正常判题期间只有一条 2s 轮询，且状态一旦变成 `paused` 就被停止，effect 依赖 `job.id` 不会因 `paused→queued` 重启。
- 暂停/继续按钮的 `action()` 会主动 `setJob` 并 `onChanged()`，所以只有点击按钮时页面才“看起来更新了”。

### 1.4 为什么暂停和继续有时有效、有时无效
- 暂停依赖 `heartbeat_at` 5 分钟判断“有没有活跃 worker”；正常的单条模型请求在 45s 内，但重试/网络慢时可能被误判。
- 继续要求状态不在 `running/queued/pausing`；如果暂停请求刚发出、worker 还没退出（仍是 `pausing`），继续会被 409 拒绝。
- `resume_job`/`retry_job` 用 `background.add_task`，若进程重启或后台任务丢失，状态停在 `queued`，再点继续又因 `queued` 被拒绝。
- 同一 job 的 `run_job` 用非阻塞锁，重复触发会直接丢弃。

### 1.5 为什么预处理报告数字不满足总数关系
- `_build_issues` 里：
  - `valid_records` = 没有 error 问题的记录数；
  - `anomalies` = **问题条数**（severity=error），不是记录数；
  - `pending_confirmation` = **问题条数**（handling_status=pending_review）。
  一条记录同时有多个问题时被多次累计，`valid + anomalies + pending ≠ raw`。
- `missing_process` 把所有没有过程的行都算进“缺失”，没有判断题目是否要求过程（选择/填空被误伤）。
- 重复记录、题目级问题被展开/未展开口径不一致，class 级统计也按问题条数算。

### 1.6 历史结果修复到底做了什么
- 只做 **A：历史结果重新解析**：查 `teacher_grade_runs.raw_response` 非空、`step_results_json` 为空、且是每个作答的最新版本；用已保存的模型原始响应重新跑 `validate_llm_result`，生成新的 `grading_version`，写 `reparsed_from` 与 attempt(stage=reparse)。
- **不调用模型**、不改原始作答、不覆盖旧记录；解析失败如实记 failed。
- 不做 B（重新调用模型判题）；B 由普通判题/失败重判完成。
- v1.5.19 起该入口从教师端判题中心移除（属于开发/维护能力），后台接口保留，避免与普通判题进度混在一起；页面左移问题随该区块移除消失。

## 2. 统一状态机

```text
preprocessing → ready（上传后自动预处理，同一任务生命周期）
ready → queued（创建判题任务）
queued → running（worker 领取）
running → pausing → paused（暂停请求；当前记录安全结束后）
running/queued/retrying → retrying（失败重判）
paused → queued → running（继续）
running/retrying → completed（有成功或待复核）
running/retrying → failed（无任何成功/复核，全部失败）
```

- 旧 `partially_failed` 迁移为 `completed`，失败数量由 counts 表达，不再把“部分记录失败”当成任务崩溃。
- 前端标签：正在预处理 / 排队中 / 正在判题 / 正在暂停 / 已暂停 / 正在重判 / 已完成 / 任务失败。

## 3. 统一进度统计

后端 `job_counts(job_id, status)` 是唯一来源：

```text
total      = 任务 item 总数
pending    = item.pending
running    = item.running
success    = item.completed 且最新判题不是 needs_review/failed
review     = item.completed 且最新判题 needs_review=1
failed     = item.failed（含最新判题为 failed 的 completed 归一）
completed  = success + review + failed
consistent = total == pending + running + completed
progress   = completed / total
```

- 重判使用 `retry_total / retry_success / retry_failed / retry_started_at` 独立进度，不改变 total，不新建任务。
- `job()` 返回 `counts`、`progress`、`retry_progress`、`counts_consistent`、`processed_consistent`。
- 前端展示：整体 658/806、成功 658、待复核 12、失败 136、执行中、待处理；重判时额外显示“失败重判 x/y”。

## 4. 修复内容与文件

### 后端 `xueban/api/xueban_teacher.py`
- `run_job`：锁冲突延迟重试，不再丢弃任务；`ensure_job_worker` 为 queued/retrying 补 worker。
- `_run_job_once`：统一 claim；暂停在记录结束后落 paused；心跳在模型调用前后更新；重判计数；终态按 success/review/failed 判定。
- `pause_job`：幂等；running→pausing，queued/失联→paused；重复暂停不报错。
- `resume_job`：仅 paused 可继续；running/queued/retrying 重复调用返回当前状态（幂等）；`background.add_task` + 轮询兜底补 worker。
- `retry_job`：独立重判进度；只重置 failed；跳过人工确认；重复调用复用当前任务；不新建 job。
- `job_counts` / `sync_job_counts` / `job()`：统一计数、进度、重判进度、一致性校验。
- `normalize_finished_jobs`：failed grade 的 item 归一为 failed；结束的 paused 任务回归 completed/failed；计数回写。
- 迁移 v8：job 重判字段 + item `retry_round` + 旧状态归一。
- 预处理：`process_requirement`、新的报告状态（valid/anomaly/pending_confirmation 互斥）、`run_preprocessing`、上传后自动预处理线程、`preprocessing/confirm` 兼容。
- 删除 `batch()` 的质量闸门阻断与 force 留痕逻辑；只要求预处理完成。
- 历史重解析：仅保留后台接口，不再出现在教师端。

### 前端 `xueban-web/src/components/BatchGrading.tsx` + CSS
- 删除质量闸门卡片/强制按钮/理由输入。
- 删除“历史结果修复/检查可重解析记录”整块（修复页面左移）。
- 预处理卡片：状态、原始/有效/异常/待确认/状态合计/对账、过程要求分布、质量标记、异常明细（学生/班级/题目/版本/字段/原因/处理/是否进入判题）。
- 进度卡片：整体 x/y、成功/待复核/失败/执行中/待处理、重判进度、状态按钮互斥。
- 轮询：任务 1s、预处理 1.5s；暂停期间继续轮询，继续后自动恢复；刷新页面恢复真实状态。

## 9. 未解决 / 限制

1. **136 条历史失败未批量重判**：131 条是模型契约（评分点分配/满分），3 条满分不匹配，1 条空答案，1 条 JSON；重判需要真实模型调用，需授权批量执行。UI 已提供“仅重试失败项（136 条）”入口与独立进度。
2. **历史 attempt 缺堆栈**：旧版本只保留原始文本，新的失败记录才有 `exception_class` 与阶段。
3. **过程判定按题型**：选择/判断/填空=只需答案；解答/计算/证明/应用/综合=要求过程；其他=可选；CSV 没有“本题是否要求过程”字段，未知题型的空过程会进待确认。
4. **预处理为同步计算的后台线程**：806 条约 1–3 秒完成；超大文件会占用一个后台线程，暂无独立队列。
5. **暂停只保证“当前记录安全结束”**：模型调用无法中途取消，最长等待一次调用（含重试）。
6. **知识依赖边为空**：与本次判题生命周期无关，真实库没有已确认前置关系。
