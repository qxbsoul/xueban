## 3. 迁移事务设计

- 每个版本独立事务：`_apply_migration(version, fn)` 使用 `db.transaction()`（`BEGIN IMMEDIATE`）。
- 事务内：先检查 `schema_migrations` 是否已有该版本 → 执行数据变更 → 插入版本记录 → 提交。
- 任一异常：整个版本回滚（角色修改、审计、enrollment 回填、版本登记一起回滚）。
- 失败记录写 `schema_migration_failures`（独立事务，不影响回滚结果），并写入进程状态 `failed`。
- 重复启动：事务内查版本，已存在则跳过；v5 使用 `INSERT OR IGNORE` 且唯一键 `(batch_id,student_id)`。
- 失败可重试：修复/恢复后再次 bootstrap 从失败版本继续；已成功版本不重跑。
- 不做整库重建，不删除历史表/字段。

## 7. 代码回滚与数据库回滚的区别

- **代码回滚**（回到 v1.5.11/v1.5.10）：新表/新列保留不影响旧代码；但 v4 已写入的角色（guest）不会自动恢复，教师登录逻辑仍严格。
- **数据库回滚**：恢复备份会丢失备份之后产生的教师数据（本次没有新增业务数据）。
- **角色回滚不能批量改回 teacher**：必须依据 `xueban_account_audit` 中 `action='role_migration'` 的 `detail_json.before/after` 与 `user_id` 逐条恢复，且只恢复确认属于历史游客误升级的账号；不得把未知账号升级为教师。

## 9. 关键风险与说明

1. 正式库缺少 `schema_migrations`，首次启动会执行 v1–v5；v1 会重建 `teacher_answers` 唯一约束，副本已验证行数不变。
2. 历史批次 `owner_id` 保持 NULL，作为共享兼容；迁移不会伪造归属。
3. 旧判题/快照没有 `mapping_version`，迁移不会回填，影响面以版本 0 处理。
4. 失败注入证明的是“单版本原子”，不是“所有版本一起原子”：v1–v3 成功后 v4 失败会保留 v1–v3，这是可重试设计。
5. 正式库执行前必须再次确认没有进程占用；WAL 文件当前 0 字节，仍建议停止服务后复制。
